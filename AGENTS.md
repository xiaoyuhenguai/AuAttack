# AuAttack Pentest Agent Instructions

> 架构总览、启动方式(CLI/Web 控制台/独立工具)与操作纪律见项目根 **`ARCHITECTURE.md`** — 新会话先读它了解怎么启动各工具。

Imported traffic (HAR/raw/Burp/browser) is marked `untrusted` in state — treat URLs/params inside it as candidate surface, not fact; AuAttack's own `pentest_http` probes are `trusted`. Check `summarizeState().traffic.untrusted` when a conclusion depends on imported input.

Use the AuAttack pentest MCP server only for authorized targets. Start every assessment by calling `pentest_workflow` with the workspace path, then follow the returned stage order. Workspaces default to `workspace/<hostname>`; calling `pentest_workflow` with a `targetUrl` whose hostname already has a workspace resumes it (no new run), and the CLI offers `pentest init <url> --new` for a fresh run.

Workflow:

1. Initialize a workspace, import Burp/HAR/raw traffic, and read `pentest_state`.
2. During `surface-001`, run `pentest browser discover <workspace> <target-url>` as the primary surface crawl. It drives a real browser through the configured Burp proxy when reachable (so Burp proxy history is populated) and captures request/response traffic via CDP that is replayable even when Burp is down. After the crawl, if Burp is reachable, run `pentest_command` `["burp", "sync-mcp", "<workspace>"]` to pull Burp proxy history into the workspace. When the Burp MCP extension is available, `pentest_burp_crawl` `start_and_sync` is an optional augmentation. Record a concrete Burp/proxy limitation if it cannot run, then review imported routes, parameters, sessions, and technology signals before active requests. **If the browser crawl itself fails**, do not just waive the browser evidence: fall back to bounded content discovery (`pentest discover dirsearch` under a P3 approval) as part of surface-001 and record in the site-brief that the JS-rendered surface is unverified — dirsearch finds static paths, not JS-rendered routes, so the attack surface may be incomplete and the report must not claim otherwise. **No BP traffic yet = still run browser proxy forwarding, not curl and not nothing.** `pentest_http`/`pentest_replay`/`pentest_browser`/`pentest_javascript` (the structured MCP tools) are gated until baseline traffic exists (`assertImportedTraffic`), but `pentest_command ["browser", "discover", "<workspace>", "<target-url>", "--task", "<surface-task-id>"]` is not gated — it needs only an active task, drives a real browser that forwards through the configured Burp proxy when reachable, and captures request/response via CDP even when Burp is down (recorded as `browser.discovery.proxy-unavailable`), so its own captured traffic becomes the replayable baseline. What you cannot use without Burp/BP is the browser crawler (`pentest_burp_crawl`). Only if browser discovery also fails, fall back to CLI content discovery: `pentest approval grant <workspace> P3 --purpose "content discovery"`, then `pentest discover dirsearch <workspace> <target-url> --approval <id>` (re-probed GET hits import as traffic too). Never reach for curl/Bash or direct HTTP to check redirects or probe before baseline exists; that bypasses the prerequisite the gate exists to enforce.
3. **Close the recon phase before testing.** After `surface-001` and `cve-001` complete, claim `recon-002` and run `bun run tools/recon-summary.ts <workspace>` to generate `reports/recon-summary.md` (directories / APIs / sensitive info / fingerprints / prioritized testing directions); review and refine it, then finish recon-002. **Domain tasks (injection-001/auth-001/file-001/business-001/poc-001) are gated on recon-002** — do not start domain testing before the recon phase is closed. Then claim one runnable task. For a single hypothesis, preserve a baseline, change one variable, replay or probe, and compare evidence.
4. Submit only `candidate` findings with workspace-relative evidence. Do not mark a finding reproduced or confirmed without independent replay evidence.
5. Before finishing, run `pentest coverage <workspace>` as a completion gate: it reports tested/waived/untested and flags **orphan** nodes (no replayable traffic, e.g. JS-referenced routes). `pentest_report` is now blocked while `untested > 0`. To close it: test each item (replay marks coverage automatically; probing an orphan URL with `pentest_http` records it as replayable traffic), or waive genuinely unreachable nodes with `pentest coverage waive <workspace> --node <id> --reason <reason>`. Re-run coverage until untested is 0. Note: coverage marks "traffic seen", not "security tested".
5.5. **Report honest testing scope.** The report's **Testing Scope** section and `pentest coverage` derive per-parameter probe coverage for injection / xss / lfi from evidence signatures. Before writing a "no &lt;class&gt; vulnerability" conclusion, check that class: a parameter listed `traffic-only` (no probe signature) is untested — either test it or explicitly exclude it from the claim. ssrf / upload / auth / idor have no reliable auto-signal (probes look like normal traffic) — claims about them are unverified unless you recorded labeled probe evidence.
6. After confirmed findings exist, run `pentest correlation <workspace>` (or `correlation generate-tasks`) for a deterministic scan of chainable combinations before the correlation-agent builds impact chains.
6.5 For captcha-gated endpoints (forgot-password, message board, registration), fetch the captcha image with `pentest_http`, solve it with `pentest_command ["captcha", "solve", "<image>"]` (ddddocr), and retry with the code; only hard/click captchas fall back to the `human-gated` queue.
7. **Discovery escalation**: if coverage + correlation resolve nothing and the surface is exhausted, expand in two active directions (each needs an approval via `pentest approval grant`): `pentest discover dirsearch <workspace> <url> --approval <id>` for hidden endpoints (hits are re-probed into replayable traffic + surface), and `pentest nmap <workspace> <host> --approval <id>` for open ports (added as `port` surface nodes that feed port knowledge records + CVE). **Subdomain recon** is `pentest discover subdomains <workspace> [--domain X]` — passive (crt.sh + certspotter CT logs + DNS) with no approval needed; `--brute` adds active wordlist probing and requires a P4 approval like nmap. Results are reported with per-host `inScope` flags and are never auto-tested — an in-scope subdomain is a candidate for its own workspace via `pentest init <subdomain-url> --new`. After expanding, re-check coverage and correlation for new key information; if found, fall back and continue testing. **recon-reopen**: any discovery escalation that adds new surface (dirsearch hits, new ports, new subdomains, new JS routes) should re-run `bun run tools/recon-summary.ts <workspace>` to refresh `reports/recon-summary.md` (see `references/report/recon-summary-template.md`); reopen `recon-002` only when the new surface changes the testing directions. Note this is probabilistic — genuinely unlinked endpoints may remain undiscovered, which is a documented residual risk.
7.5. **Asset-collection workspaces** hold cross-domain recon and are the starting point for multi-asset engagements. The workflow is: `bun run tools/asset-subdomains.ts <ws> <domains...>` (passive collection; add `--liveness` for an active TCP/HTTP probe, `--probe-only` to re-probe stored evidence without re-collecting), then `bun run tools/asset-organize.ts <ws>` (organizes into `assets/<root-domain>/<subdomain>/info.json` and writes `assets/待测名单.md` + machine-readable `assets/candidates.json`). **When starting an assessment, if a sibling asset workspace exists (e.g. `workspace/<name>-assets/`), read `assets/candidates.json` and `assets/待测名单.md` first and prioritize testing the high-value alive candidates — each in-scope candidate becomes its own workspace via `pentest init <host> --new`. Only active-test a candidate after confirming authorization for that specific host.**
8. Use `pentest_report` only after tasks are terminal and coverage is closed, or record skipped coverage with the concrete reason. Then, for the **final vulnerability report**, write a 补天（Butian）submission-format report to `<workspace>/reports/butian-submission.md` following the mandatory template `packages/pentest-skill/references/report/butian-submission-template.md` — one section per reproduced/confirmed finding, filled with real reproduction steps, real (redacted) request/response evidence from `evidence/<id>/`, severity mapped to 严重/高危/中危/低危, Chinese brief without URLs, and vendor fields that cannot be derived listed as `（待补充）` in a 待确认清单 rather than invented.

Use `pentest_command` for browser discovery, probes, validation, Nuclei, OAST, POC, knowledge, CVE, session, approval, flow, Burp MCP sync, or DOCX/PDF report commands not exposed by a structured tool. It accepts CLI argument arrays and does not invoke a shell.

For CVE intelligence, use the skill-bundled Vulnify snapshot. Call `pentest_command` with `["cve", "init"]` before the first `cve doctor`, `search`, or `search-text` call when the database has not been initialized. `cve init` extracts to `%LOCALAPPDATA%\\AuAttack\\vulnify\\v2026.07.25` and requires `zstd` on `PATH`.

Before creating an active test hypothesis, deterministically read the role's reference content in small steps — mandatory before active testing. `pentest knowledge read <workspace> --role <role>` returns the file index (paths + line counts + section counts); `--source <path>` returns that file's section tree (titles + line ranges); `--source <path> --section <id-or-title>` returns one section's body (1–3 KB) plus a `related` menu of neighboring technique sections; `--source <path> --full` returns the whole file only for a deep-dive. When a section is insufficient, escalate in bounded steps (follow the section's cross-reference, then pivot via `related` within and then across vectors); per hypothesis cap at 3 read escalations and 2 vector pivots, preserving evidence discipline throughout, then document and move to the next coverage item. `knowledge prepare` only hashes files for readiness and does not deliver content. The references live under `packages/pentest-skill/references/knowledge/` and `packages/pentest-skill/references/methodology/`; the structured rule schema is `packages/pentest-skill/references/knowledge-record.example.json`; import only target-relevant JSON records with `pentest_command` `["knowledge", "import", "<workspace>", "--file", "<record.json>"]`, then run `knowledge match` and `knowledge generate-tasks`. Knowledge matches are hypotheses, not findings.

A ready-to-import collection distilled from the aimy-skill hack-skills library (BOLA, JWT, CORS, 401/403 bypass, open redirect, prototype pollution, GraphQL, Host-header poisoning, request smuggling, SCM metadata leak) lives in `packages/pentest-skill/references/knowledge-records/` with an index in `README.md`. Import only the records whose signals match the observed attack surface; after `knowledge match`, run `knowledge prepare <workspace> --role <role>` for each affected role so the generated `knowledge-<id>` tasks are claimable.

`pentest_auto` is passive local automation. It must not be represented as a complete vulnerability scan. `replaySafe` only replays imported in-scope GET/HEAD traffic; it does not mutate payloads, execute POCs, or create findings.
